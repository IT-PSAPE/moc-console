# Neon database baseline

`build-fresh-database.sh` installs the complete MoC schema only when the MoC-owned `public`, `moc_private`, and `moc_auth` namespaces have no relations. It leaves Neon's managed `neon_auth` schema untouched. The bootstrap applies the Better Auth tables, constrained database roles, the standalone final-state domain schema, upload tables, and broadcast revision tables, then runs the independent catalog verifier in the same transaction. The enum preflight is the only separately committed additive step because PostgreSQL requires a new enum label to commit before use.

`20-domain-final.sql` is the authoritative final-state domain baseline. It contains the approved schema, functions, policies, and seed rows, and has no runtime dependency on migration history. It rewrites all application actor checks through `moc_private.actor_id()` and links public profiles to `moc_auth."user"`. Better Auth profile creation and email synchronization run through auth service hooks.

Application authorization runs through the API. Upload metadata lives in `moc_private`, while object bytes are served through the storage implementation. Broadcast revision rows and SSE provide durable change delivery. Apply with a migration-owner connection; the bootstrap grants that connection membership in `moc_app`, `moc_public`, and `moc_worker`, which `withActor` selects transaction-locally. Production API and worker URLs should use dedicated credentials limited to their respective role memberships. `moc_app` and `moc_public` retain RLS; only `moc_worker` bypasses it. Do not expose database URLs to frontends.

`node neon/database/import-domain-data.mjs` remains available for a direct PostgreSQL-to-PostgreSQL import. The Supabase cutover uses `node neon/database/import-supabase-snapshot.mjs` with the versioned source snapshot exported into a mode-0600 file. Its dry run validates the exact 49-table allowlist, source project, table columns, row keys, profile/auth identity parity, verified bcrypt hashes, and the three public Storage bucket inventories. It writes a mode-0600 target-state plan with the target fingerprint and sanitized row counts. It never prints row values, password hashes, OAuth secrets, or database URLs. Target-only request-link and scheduled-message columns are omitted from source inserts so their database defaults apply. Storage object bytes and bucket content are transferred separately by the storage cutover procedure.

The snapshot records PostgreSQL source types and per-table PostgreSQL MD5 fingerprints. The importer validates each fingerprint against both the typed snapshot payload and the imported target projection before commit. Two explicit target type widenings are allowed: occurrence `send_on` preserves its source date as midnight UTC in the target timestamp column, and schedule `expiry_hours` widens source integer values to numeric without changing their value. The fingerprint projection casts occurrence `send_on` back to its source date under a UTC session, preserving the original calendar date during verification.

Review the dry-run source and target counts and take a recoverable Neon backup before applying. Applying requires both flags plus the reviewed plan: `node neon/database/import-supabase-snapshot.mjs --snapshot output/supabase-migration/source-snapshot.json --plan output/supabase-migration/target-plan.json --apply --confirm-replace-target`. The importer rechecks the snapshot hash and target fingerprint inside a transaction before replacing source-owned domain rows, profile/auth identities, and credential accounts. It preserves source UUIDs and bcrypt passwords, clears old target sessions and verification tokens, imports no sessions, restores and verifies foreign keys, and compares every source row before commit. Any failure rolls the transaction back. Do not apply until cutover approval is explicit; keep scheduled and background workers stopped through database and storage cutover.

The snapshot contains credential hashes and private OAuth values. Restrict it and the target-state plan to the migration operator; never commit them, attach them to tickets, or print their contents. Unexpected or missing source tables fail closed and require updating and reviewing the importer allowlist instead of silently skipping data.

To write a fresh target, run `node neon/database/import-domain-data.mjs --apply --confirm-empty-target` with a migration-owner connection. The importer takes a repeatable-read source snapshot, rejects a non-fresh target, disables target user triggers and drops imported-table foreign keys inside one transaction, copies rows in primary-key order, restores triggers and sequences, recreates and validates foreign keys, then compares every source and target row fingerprint before commit. Any error rolls back the import. Keep scheduled and background workers stopped until the import and parity checks finish. Identity and object-byte transfer remain separate controlled steps. Do not run `--apply` against production until source/target DSNs and the cutover window have been explicitly supplied.

`node neon/database/verify-import-parity.mjs` performs a read-only post-import comparison for the public domain tables and mapped OAuth rows. The import itself performs the stricter full allowlist parity check before commit.

Request links are installed by `request-links.sql`. Apply this additive migration with a migration-owner connection before deploying the API/console changes that read `request_id` on equipment bookings, venue bookings, streams, and Zoom meetings. It retains independent records, validates the request's workspace, and detaches links when a request is deleted. No existing lifecycle, reservation, or provider data is rewritten. For fresh databases, apply it after `build-fresh-database.sh`. For a legacy domain import, apply it after importing and verifying parity (the importer intentionally requires matching source/target column layouts).

Undated checklist runs are enabled by `checklists-undated.sql`. Apply this additive migration with a migration-owner connection before deploying application changes that create runs without `scheduledAt`. It only drops the `NOT NULL` constraint from `checklists.scheduled_at`; existing values remain untouched. The baseline schema already allows NULL for fresh databases, and applying the migration after `build-fresh-database.sh` is safe and idempotent.

Direct scheduled Telegram messages and ordered attendee IDs are enabled by `scheduled-direct-messages.sql`. Apply it with a migration-owner connection before deploying the API/console changes. Fresh databases apply it after `20-domain-final.sql`; it allows schedules without a saved template and stores attendee ordering on schedules and occurrences. Existing saved-template schedules retain their current audience behavior. For a legacy domain import, import and verify the unchanged source/target schema first, then apply this migration; the importer requires identical column layouts and this migration intentionally adds columns.

Supabase Storage is transferred separately with `node neon/database/download-supabase-storage.mjs`. It reads the protected source snapshot/admin inventory and `neon/.env.local`, writes mode-0600 objects and a transfer manifest under `output/supabase-migration`, and verifies every byte count and SHA-256. The manifest registers only objects referenced by imported app rows whose owner, workspace, and purpose are proven; unreferenced objects are copied under a private `supabase-migration/` prefix with their complete source Storage row retained in S3 metadata. A referenced object with unresolved ownership or purpose blocks transfer. Review the protected manifest before any cutover.

`node neon/database/upload-neon-storage.mjs` performs a local-only validation. Its `--apply` mode conditionally creates each private S3 object, refuses a differing existing object, and reads the stored bytes and original Storage metadata back for verification. `node neon/database/register-neon-storage.mjs` also defaults to local validation. `--rehearse` requires an explicit loopback `NEON_MIGRATION_REHEARSAL_DATABASE_URL`, runs the real metadata registration and URL rewrite statements, and rolls the transaction back. `--apply` first verifies all remote object bytes and metadata, then registers only referenced app objects and rewrites exact imported `users.avatar_url` and `broadcast_items` rows in one serializable transaction. It checks source row values and ownership context, permits only already-applied identical rewrites on retry, and rolls back on any conflict. Do not use either `--apply` flag until the database cutover has been explicitly approved and the reviewed manifest matches the source inventory.
